# ShortCut hosted review: always-on demo + time-limited live generation

Date: 2026-11-13. Status: approved approach (A), design for review.

## Intent and why

Manila Hack panelists need a **hosted link** to check and review ShortCut after the live demo. Today the full app only runs on the
owner's laptop (API + Codex CLI + GPU voices), exposed through a Cloudflare quick tunnel; the laptop cannot stay on for the review
period. We want:

1. A link that **always works**, for anyone, with no laptop: the editor plus ready-made videos (demo mode).
2. **Real live generation for panelists only**, for **one week**, running in a cloud container that uses the owner's Codex
   sign-in (their Codex credits), unlocked by a **shared reviewer code** sent in the email to panelists.
3. A **log of who used live generation and when**, readable by the owner on a private page.
4. Anyone without a valid code, or when the backend is down/expired, **falls back to the demo** without errors.

Success: a panelist opens the Vercel link, sees the demo instantly; enters the code + their name, generates a real video; the
owner sees "Maria · Nov 14 21:40 · new video · 'jeepneys' · ok" on the admin page. After 7 days the live part switches itself off
and the owner's Codex sign-in is removed from the server.

## Goals

- Always-on demo on Vercel that works with the backend completely offline.
- Live generation (plan, edits, voice, images, 3D models, export) for code holders, served by a Railway container running the
  existing `server.py` with Codex CLI signed in through the owner's `auth.json`.
- Server-side gate: every live request must carry a valid reviewer code (and a name) before the 7-day expiry; checked on the backend.
- Usage log (name, time, action, topic, success) persisted on a Railway volume; `/admin` page with an admin code; CSV download.
- Automatic expiry: after the window the backend refuses live requests and deletes the Codex sign-in file.

## Non-goals

- Per-panelist codes or accounts (owner chose one shared code + a name field).
- Making the hosted container match the laptop exactly: no GPU, so no Qwen voices and no Blender shots.
- Rebuilding the editor or changing the generation pipeline. (Broader product improvements are a separate, later design.)
- Hiding the backend URL. It is visible in any browser's network tab; protection comes from the server-side code check.

## Anti-goals (would be a failure even if it "works")

- The Codex sign-in, reviewer code or admin code appearing in the Vercel bundle, the repo, logs or any response.
- Anyone without the code spending Codex credits (including through routes other than "generate").
- The demo breaking or showing errors when the backend is asleep, down, out of credit, or expired.
- The owner's credentials still on the server after the review week.
- Storing IP addresses or device fingerprints in the log.

## Constraints

- Owner's Codex account: ChatGPT sign-in with ~498 credits (monthly allowance used up; resets Dec 12). One generation costs well
  under one credit. Using a personal ChatGPT-plan sign-in behind a hosted service may conflict with OpenAI's terms; the owner has
  been told and chose this, limited to one week with automatic removal.
- Hosting accounts (Railway, Vercel) are created and signed into by the owner; secrets are pasted by the owner into the host's
  secret settings. The builder never handles the owner's passwords.
- Existing contracts must keep working: the Plan JSON (`web/src/video/Video.tsx`), `server.py` routes, the laptop setup
  (`BLOCKCUT_AI=codex`, `.env`), the demo instance (`BLOCKCUT_DEMO=1`, `samples/<name>.ready.json`).
- Slow routes already answer with keep-alive spaces (`Handler.reply_slow`); the frontend's `api()` treats a 200 `{"error"}` as failure.
- Vercel already builds `web/` with rewrites from `web/vercel.json` (generated by `deploy/set_tunnel.py`); bundles go to `/_app`.

## Approaches considered

- **A. Vercel site + Railway backend (chosen).** Vercel hosts the editor *and* the demo content (pre-built videos and their media,
  bundled in the site). Vercel rewrites `/api` and media paths to the Railway backend. Missing/invalid/expired code or an unreachable
  backend → demo mode. Two deploy targets, but the demo survives any backend failure, which is the main reason for doing this.
- B. Everything on Railway, Vercel only redirects. One deploy, but if Railway sleeps, crashes or runs out of credit the "always-on"
  demo is gone too. Rejected.
- C. Gate and log as Vercel serverless functions in front of Railway. A second backend with no benefit. Rejected.

## Design (decided)

### 1. Access model
- **Reviewer code**: one shared code (env `REVIEWER_CODE`), emailed by the owner to all panelists.
- **Name**: required on first unlock (2-40 chars, trimmed); remembered in the browser with the code.
- **Window**: env `REVIEW_EXPIRES_AT` (ISO 8601 with timezone), set to 7 days after the email goes out. The owner can end it early
  by changing the env var or removing `REVIEWER_CODE`.
- **Wrong code**: "That code isn't valid or has expired"; the site stays in demo mode. After 5 wrong tries the server makes that
  client wait 60 s (in-memory per client address; the address is never written to disk or the log).
- **Admin code**: env `ADMIN_CODE`, only reads the log; never unlocks generation.

### 2. Backend gate (in `server.py`, Railway only)
- Active when `REVIEWER_CODE` is set (the laptop and demo instance run unchanged without it).
- New `POST /api/session {code, name}` → `{ok: true, name, expiresAt}` or 401 `{error}`. Constant-time code comparison.
- Every request that spends AI, credits or server work requires headers `X-Reviewer-Code` and `X-Reviewer-Name` with a valid code
  before expiry; otherwise 401 `{"error": "locked"}`. Gated: `/api/plan`, `/api/edit`, `/api/voice`, `/api/assets/find`,
  `/api/assets/search`, `/api/assets/import`, `/api/assets/scrape`, `/api/assets/upload`, `/api/render`, `/api/styles/from-url`,
  `/api/footage/*`, `/api/shots/render`. Ungated (read-only): `GET /api/styles`, `/api/voices`, `/api/models3d`, `/api/assets`,
  render/style job status, and static media.
- **Daily safety cap** (my call): at most 80 gated actions per day across all reviewers (env `REVIEW_DAILY_CAP`), then
  "Today's live limit is reached; the demo still works." Protects credits from runaway use.
- **Expiry** (my call: checked on every request and at startup, so it works even if the app sleeps; an hourly timer is only
  a bonus): if now > `REVIEW_EXPIRES_AT`, delete the Codex sign-in file, and every gated route answers 401 "locked". The container
  keeps serving read-only routes so the site's demo assets still load.
- **Shared library** (my call): `GET /api/assets`, `/api/assets/delete` and `/api/styles/delete` are gated too, so uploads and the
  asset list are only visible to code holders. Reviewers share one library on the server; that's acceptable for a review week.

### 3. Usage log
- Append-only JSON lines at `/data/review-log.jsonl` (Railway volume mounted at `/data`).
- One entry per gated request: `{time (UTC ISO), name, action, topic/instruction (first 120 chars), ok, seconds}`; also each
  successful and failed `/api/session` unlock (name, ok). No IP, no user agent.
- `GET /admin`: a small server-rendered HTML page; asks for the admin code (form POST, then a session cookie scoped to `/admin`,
  HttpOnly, 12 h). Shows a table newest first in Manila time, counts per name, and links to `GET /admin/log.csv`.

### 4. Railway container
- Dockerfile at repo root: Python 3.11 + venv deps (`requirements.txt`), Node 22 for Remotion export and the Codex CLI
  (`npm i -g @openai/codex`), Remotion's Linux Chrome dependencies, FFmpeg not required (Remotion bundles its own).
  faster-whisper `base` model downloaded at build time. Runs `server.py` with `BLOCKCUT_AI=codex`, `PORT` from Railway.
- Codex sign-in lives on the volume (`CODEX_HOME=/data/codex`), so the token refreshes Codex writes survive restarts (my call).
  It is seeded from the secret `CODEX_AUTH_JSON` only if no file exists yet and the window is still open; expiry deletes it there.
- Voices: Edge TTS (Qwen is unavailable without the speech.cpp binary and GPU; `tts.engine_status()` already reports that).
- Persistent volume `/data` for the log; generated media (`web/public/{assets,media,models3d,renders,footage}`) may be ephemeral.
- Blender shots are not installed; `/api/shots/render` reports "not available on the hosted version". YouTube style extraction
  is attempted but may fail (YouTube often blocks cloud IPs); it must fail with a clear message.
- `server.py` must listen on `0.0.0.0` and Railway's `PORT` when set (today it binds localhost and `BLOCKCUT_PORT`).

### 5. Vercel site (demo + live)
- `web/vercel.json` rewrites `/api`, `/assets`, `/media`, `/music`, `/footage`, `/models3d`, `/renders` to the Railway URL
  (generated by `deploy/set_tunnel.py` or a sibling script). `/admin` also rewritten so the owner can use the Vercel domain.
- **Demo content is bundled in the site** under `web/public/demo/`: each ready video's plan JSON plus its photos, voice audio,
  3D models and music, with plan URLs rewritten to `/demo/...` so they load from Vercel, not Railway. At least the ube video
  (`samples/ube.ready.json`); the builder adds two more ready videos built with the real pipeline (my call: a jeepney explainer
  and a 3D showcase), and a pre-rendered MP4 of each for "Download video" in demo mode.
- **Mode switch** in the frontend: on load, call `GET /api/session/status` (ungated; reports whether live review is open). Live mode
  only when the backend answers, review is open, and the browser holds a code + name that `/api/session` accepted. Otherwise demo.
  Any 401 "locked", 5xx or network failure on a live call drops to demo mode with a short notice instead of an error.
- **Demo mode behaviour**: start screen shows the starters; Generate on a topic matching a demo video plays the normal cooking
  screen for ~4 s and opens that video; other topics show "Live generation is for reviewers. Try one of the demo videos" with the
  demo starters. The editor works fully client-side (timeline, inspector, styles, theme, playback). AI edits, voicing new lines,
  image search and MP4 export show "Needs a reviewer code" with an "Enter code" button; export offers the pre-rendered MP4.
- **Unlock UI**: a small "Reviewer access" button on the start screen and in the editor header opens a dialog with code + name.
  On success: a "Live · <name> · until <date>" chip. A "Sign out" link clears the stored code.

## Decisions after the builder check (owner said "go ahead" with the proposals)

- **Order**: ship the always-on Vercel demo first (usable link as early as possible), then the Railway live backend. The review
  window starts when the owner sends the email; nothing in the build depends on that date.
- **Codex sign-in**: the server gets its **own** sign-in (device-code login run once from Railway's console into `/data/codex`), so
  token refreshes on the laptop and the server don't log each other out. `CODEX_AUTH_JSON` seeding stays as a fallback.
- **Demo content**: build on the existing untracked `web/public/demo/` (index.json with keyword matching, ube/jeepney/tower_defense
  plans, styles.json, media), checking and completing it rather than starting over.
- **Railway**: Hobby plan, ~2 GB RAM, sleeping off. If export proves unreliable in the container, MP4 export is demo-only (the
  pre-rendered file) on the hosted version; the laptop keeps full export.

## Left to the builder

- Exact Dockerfile layering, base image, and how Remotion's Chrome is installed on Linux.
- Storage format of the per-client wrong-try counter, and log rotation (not needed at this volume).
- Copy and styling of the unlock dialog and notices, consistent with the current editor (light/dark themes).
- How demo plans are matched to free-text topics (keyword lists like `samples/*.json` are fine).
- Which three demo videos exactly, as long as one is the existing ube video and one uses a Polyfork 3D model.
- Test approach: a runnable self-check for the gate/expiry/log logic, plus one end-to-end run on Railway with a test code.

## Owner actions (cannot be done by the builder)

1. Create a Railway account and project from the GitHub repo; add a volume at `/data`.
2. Paste secrets in Railway: `CODEX_AUTH_JSON` (contents of `C:\Users\<you>\.codex\auth.json`), `REVIEWER_CODE`, `ADMIN_CODE`,
   `REVIEW_EXPIRES_AT`.
3. Confirm the Vercel project (Root Directory `web`) and send the panelists the email with the link and the reviewer code.
